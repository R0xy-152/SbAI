# 21 — 运营监控与反馈分析落地方案

> **文档状态：** Active
> **日期：** 2026-09-04
> **前置：** docs/19 序章、docs/20 对开发者的话、docs/18 邀请码账号
> **动机：** 把 gal 从「AI 游戏工程 Demo」升级为「有真实玩家数据、反馈分析与实验结论的产品案例」（P1 主线）。事实依据：`validation-results/eval-memory-recall-realdata`（真实提案率 3.2%）、`eval-ab`（单次 8 用例噪声 ≥ 臂间分差）。

## 1. 目标与边界

- 建立轻量内部运营闭环：**埋点 → 看板 → 反馈分类 → 人工抽检 → 一次数据驱动迭代**。
- 不新增玩家可见功能；不动剧情内容（AGENTS.md 冻结边界）；不引入 pgvector/RAG/Redis 等禁止依赖。
- 诚实口径：事件数据是管线演示，样本小时不作为统计结论；反馈分类是「LLM 分类器 + 人工抽检精度」，不包装成自主 Agent。

## 2. 事件字典（埋点）

| 事件名 | 触发点 | payload |
|---|---|---|
| `prologue_start` | 首次 advance 进入序章 | `{story_id}` |
| `prologue_visit_chosen` | 探班选择提交 | `{character_id, order}` |
| `prologue_visit_completed` | 角色篇完成（离开 branch 阶段） | `{character_id}` |
| `prologue_choice` | 任意序章选项 | `{choice_id, option_id, label}` |
| `prologue_completed` | chat_choice 提交（序章完成） | `{chat_character_id}` |
| `ai_chat_enter` | 序章完成后第一条 AI 对话（每会话一次） | `{character_id}` |
| `ai_chat_turn` | AI 回复成功产出（含安全回落） | `{character_id, provider, validation, scripted}` |
| `ai_chat_error` | Provider 请求失败（503） | `{error_type}` |
| `ai_chat_blocked` | Presence Gate 拦截（403） | `{reason}` |
| `validation_reject` | 校验拦截（确定性门 / 一致性门） | `{gate, reason, character_id}` |

聊天延迟与 token 用量不进事件 payload，落独立表 `chat_metrics`（见 §3）。

## 3. 存储

复用 PostgreSQL（`GAL_POSTGRES_DSN`），新表由 `OPS_SCHEMA_SQL` 建立（与 auth 仓库同模式，幂等 CREATE IF NOT EXISTS）：

- `game_events(id, event_name, session_id, user_id, character_id, payload JSONB, created_at)` + 事件名/会话索引。
- `chat_metrics(id, session_id, user_id, character_id, provider, latency_ms, prompt_tokens, completion_tokens, cache_hit_tokens, cache_miss_tokens, cost_cny, created_at)`。**成本口径**：按 DeepSeek 公开价格占位（缓存命中 ¥0.5/M、未命中 ¥2/M、输出 ¥8/M，可用 `GAL_OPS_PRICE_INPUT` / `GAL_OPS_PRICE_CACHE_HIT` / `GAL_OPS_PRICE_OUTPUT` 覆盖），公式 `(miss×input + hit×cache_hit + completion×output)/1e6`；token 原始数一并落库，价格口径变化时可重算。
- `feedback_analysis(id, note_key, dedupe_key, topic, severity, scene, is_duplicate_of, summary, model, status, raw_json, created_at)`——**原始留言永远留在 `developer_notes` 作证据**，分析结果只引用 note_key。
- `feedback_annotations(id, note_key, topic_correct, severity_correct, annotator, created_at)`——人工抽检标注。
- **note_key = `developer_notes.session_id`**（docs/20：该列 UNIQUE，留言唯一且可在 Python 侧直接取得，不需要回读数据库主键）。

测试/无库环境使用内存实现（MemoryOpsRecorder / MemoryFeedbackStore），行为与 PG 实现一致。

## 4. 埋点点位（代码缝合）

- `GameOrchestrator` 新增可选构造参数 `ops: OpsRecorder | None`（None 保持既有测试行为），运行时注入实例。
- `story_advance`：advance 前取 `runtime.snapshot`；advance 后对比——before 为 None → `prologue_start`；before.phase == "branch" 且 after 不再是 branch → `prologue_visit_completed`。
- `story_choose`：选项提交 → `prologue_choice`；按 `choice_id` 追加 `prologue_visit_chosen`（order = 已访问数+1）或 `prologue_completed`。
- `_handle_turn`：序章后日谈会话首轮 → `ai_chat_enter`（每会话一次）；`validation_reject` 在确定性门与一致性门两处拒绝分支记录。
- `api/chat.py`：ProviderError → `ai_chat_error`；CharacterUnavailable → `ai_chat_blocked`。
- 延迟/token：`LLMProvider.complete` 增加可选 `metrics: dict | None` 出参（接口级可选参数，Mock/Anthropic 一并兼容）；`CharacterRuntime.respond` 透传。DeepSeek 适配器累加每次调用（含修复重试与 thinking 降级重试）的延迟与 usage。Orchestrator 在回合成功后写 `ai_chat_turn` 事件 + `chat_metrics` 行。

## 5. 看板（内部工具，GAL_OPS_TOKEN 门禁）

- 页面 `GET /ops`（单文件 HTML，无构建、无图表库），数据端点全部要求 `x-ops-token` 或 `?token=` 等于 `GAL_OPS_TOKEN`（未配置时端点 503 关闭）。
- `GET /api/ops/funnel`：每会话最远阶段分布（started → ≥1 visit_chosen → ≥1 visit_completed → 3 visits completed → prologue_completed → ai_chat_enter）→ 序章完成漏斗与**主要流失节点**；按角色拆分的访问完成率。
- `GET /api/ops/preferences`：首访角色分布、聊天角色选择分布。
- `GET /api/ops/ai`：成功率（turn / (turn+error)）、延迟 P50/P95（Python 分位数，样本小时标注 n）、总成本、单次完整体验平均成本（≥1 次 ai_chat_enter 的会话）、validation_reject 计数与 gate 分布。
- `GET /api/ops/events`：原始事件流（按 event_name/limit 过滤）——**可追溯**。
- `GET /api/ops/feedback`：留言 + 分析 + 去重组 + 抽检 Precision。
- CLI `python -m app.ops.cli report` 输出同口径文本报告（服务器容器内可用，无浏览器场景）。

## 6. 反馈分类 Agent（LLM 分类器 + 人工抽检）

- `FeedbackClassifier`：对每条 `developer_notes`（跳过已分析）用 DeepSeek 结构化输出（json_object）分类：`dedupe_key / topic / severity / scene / is_duplicate_of / summary`；解析失败记录 `status=failed` 不重试。topic 枚举：bug / experience / story_content / character / difficulty / praise / complaint / suggestion / other；severity：low / medium / high。
- 去重：同 `dedupe_key` 的后续留言标记 `is_duplicate_of` 指向首条。
- 人工抽检：`POST /api/ops/feedback/annotate`（note_key + topic_correct / severity_correct 布尔）→ `Precision = 正确标注数 / 已标注数`，按字段分别计算；**抽检集不足 50 条时按实际量全量标注并如实记录 n**。
- 分类不修改、不删除原始留言；分析行存 `raw_json` 全量模型输出，可追溯。

## 7. 一次数据驱动迭代（协议）

1. 部署本方案（埋点+看板）后，招募 10–20 名体验玩家（邀请码发放，用户执行）。
2. 观察 ≥3 天（或 ≥15 个完成会话）：找出漏斗最大流失节点 / Top 反馈主题。
3. **只选一个问题**，改前记录基线指标（如「某角色篇完成率」）。
4. 修改 → 部署 → 再观察 ≥2 天 → 前后对比（完成率/主题相关反馈频次）。
5. 结果写入 `validation-results/ops-iteration-1/result.md`（前后数据 + 结论 + 限制）。

## 8. 验收

- 7 个埋点点位在真机链路各产生对应事件（本地用 memory recorder + pytest 断言事件序列）。
- 看板四端点（funnel/preferences/ai/events）在样例数据上数值正确；无 token 时全部拒绝。
- 分类器对样例留言产出合法字段并保留原始留言；抽检标注后 Precision 计算正确。
- 558 既有测试不回归；新增测试覆盖事件序列、分类、看板聚合。

## 9. 已知限制

- 事件与指标为**事后**记录：写失败只记日志，绝不影响游戏回合（与 Auto Save 副作用同约定）。
- 真实流量小（当前 18 账号），漏斗/分位数是管线演示口径；P50/P95 在 n<50 时输出 n 供诚实引用。
- 分类器与生成同模型（DeepSeek），人工抽检是当前唯一的独立评判。
- `ai_chat_error` 的 session_id 可能为 None（异常发生在会话铸造后、返回前），按请求携带值记录。
