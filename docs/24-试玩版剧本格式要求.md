> **文档状态：** ACTIVE（v1 以 docs/23 方案与已实现代码为事实依据；正式对白/Evidence/答案草稿待用户提供后对齐）
> **日期：** 2026-09-05
> **职责：** 本文是试玩版「剧本 / 剧情内容」的**编写格式契约**：内容由哪几类构成、每个结构长什么样、放在哪里、受哪些校验约束、正式草稿接入时要动哪些代码。本文是 docs/23 的内容格式配套文档，不替代 docs/23 方案本身。

## 0. 结论（现状一句话）

试玩版「剧本」没有独立的正式内容文件，正式对白/答案仍是 **Fixture**；但自 2026-09-05 起，这些 Fixture 已被组织成**唯一的、载入即全量校验的内容表** `backend/app/trial/content.py::TRIAL_CONTENT`（台词、场景、Evidence、Deduction 判定、Branch 线路、转移目标、字面量、checkpoint 全部在表内），`runtime.py` 只执行这份已校验的表，不再内含任何判定/分支/字面量逻辑。因此「试玩版剧本格式要求」分两层理解：

1. **内容表契约（v1，代码已消费）**：`TRIAL_CONTENT` 各表结构与字段约束，本文 §3–§7 逐条给出；**换正式剧本 = 改内容表，不动 Runtime**；
2. **为正式草稿预留的扩展位**：与主线固定剧本（docs/17 / 07 剧本 / `story_content.py`）格式的差距（多句节拍 / emotion / 选项等），本文 §8 给出，等草稿定形状后接入。

正式对白草稿（用户手头稿）到位后，本文 §9–§10 作为逐条对齐与落地的检查清单。

## 2. 试玩版「剧本」由哪几类内容构成

与主线固定剧本（台词即全部）不同，试玩版的"剧本"需要覆盖五类内容，且**只有第 1 类更像传统台词稿**：

| 编号 | 内容类 | 现有载体 | 状态 |
|---|---|---|---|
| C1 | **台词节点**（每 phase 一句，`speaker_id/label/text`） | `TRIAL_CONTENT.lines` + `phases[].line_id` | Fixture |
| C2 | **场景与角色站位**（背景图、在场角色、slot） | `TRIAL_CONTENT.scenes`（`phases[].scene_id` 引用） | Fixture 素材标记 |
| C3 | **Evidence 定义**（标题 4–5 字 + 详情） | `TRIAL_CONTENT.evidence` | Fixture |
| C4 | **Deduction 判定 + Branch 映射**（正确组合、等价表达、evidence 上限、A/B 归属） | `TRIAL_CONTENT.deductions` + `routes` | 已内容化（值仍 Fixture） |
| C5 | **交互/演出字面量**（停止服务文案、引导提示、按钮字） | `TRIAL_CONTENT.phases[].interaction` | 已内容化（停止服务最终文案待确认） |

**结论：** 五类内容均已收进同一张内容表，Runtime 不再内置任何判定/分支/字面量。正式剧本接入 = 只改 `TRIAL_CONTENT` 并重新过校验；C2/C5 属表现/演出配置，应随正式稿一并锁定（尤其 C5 的停止服务最终文案）。

## 4. 当前消费形状（字段以代码为准）

### 4.1 台词节点（C1）—— 内容表结构（当前仍是单句；扩展位见 §8）

```python
# TRIAL_CONTENT["lines"]（phase key → line dict）
"opening_warm_chat": {
    "speaker_id": "origin_ai",        # 内部 id
    "speaker_label": "████",          # 玩家可见名（遮蔽）
    "text": "…",                       # 一句台词
}

# 对应 TRIAL_CONTENT["phases"] 中的一行
{
    "phase_id": "opening_warm_chat",
    "scene_id": "TRIAL_OPENING",
    "line_id": "opening_warm_chat",
    "interaction": {"kind": "advance", "label": "继续"},
    "advance_to": "opening_input",
    # 其余命令目标 / checkpoint / on_enter 字段见 §7 与 §3.2
}
```

下发 node 形状（= 前端 `TrialLine`，仅 4 字段，**无 emotion、无多句**）：

```ts
interface TrialLine {
  kind: 'line'
  speaker_id: string
  speaker_label: string
  text: string
}
```

规则要点：

- **一条台词 = 一个 phase**：有台词的 phase 行必须带 `line_id == phase_id` 且 `lines` 里有该 key；缺 key / 引用错位 → import 时校验拒绝启动（fail closed）；
- `kind` 恒为 `"line"`，由 Runtime 注入，内容侧不写；
- `speaker_label` 是**玩家可见名**，`speaker_id` 是内部 id——两者都要求内容给出；
- `origin_ai` 的可见名必须为遮蔽标识（默认 `████`），见 §4.3。

### 4.2 场景（C2）

```ts
interface TrialScene {
  scene_id: string
  background: string          // 如 "/backgroud/background_ai.png"
  video?: string              // 可选：开场特写视频（如 "/backgroud/kei_opening_720p.mp4"），纯表现层
  poster?: string             // 可选：视频首帧静态回退（reduced-motion/低速/加载失败）
  music?: string              // 可选：开场音乐（如 "/backgroud/aira_full.m4a"），与视频同帧起播
  fixture_art: boolean        // true = 占位素材，正式替换后改 false
  characters: TrialCharacter[]
}
interface TrialCharacter {
  character_id: string
  display_name: string
  slot: 'LEFT' | 'CENTER_LEFT' | 'CENTER' | 'CENTER_RIGHT' | 'RIGHT'
}
```

现状只有 3 个场景；**每个 phase 行自带 `scene_id`**（不再按 phase 前缀猜场景）：

| 场景 | 在场角色（slot） | 覆盖 phase |
|---|---|---|
| `TRIAL_OPENING`（`background_ai.png`） | `origin_ai`（CENTER，显示 `████`） | 全部 `opening_*` 与 `not_started` |
| `TRIAL_FRAGMENT_01_DEEPSEEK`（`background1.png`） | `deepseek`（CENTER） | `fragment_01_deepseek_intro`、`fragment_01_first_reasoning` |
| `TRIAL_FRAGMENT_01_GROUP`（`background1.png`） | `deepseek`(LEFT)、`chatgpt`(CENTER_LEFT)、`claude`(CENTER_RIGHT)、`doubao`(RIGHT) | 其余 fragment phase（含两个 handoff） |

注意：当前「全人物集合」= DeepSeek/ChatGPT/Claude/豆包 四人，**不含 origin_ai**；原初 AI 是否算入集合是 docs/23 §15 待用户确认项。

### 4.3 遮蔽规则（涉及 C1/C2 的共同硬规则）

- 角色内部 id 用 `origin_ai`；任何**玩家可见字符串**（`speaker_label`、`display_name`、History、存档标题、无障碍文本）不得出现「原初 AI」或可还原真实称呼的文字；
- `content.py::validate_trial_content()` 在 import 时扫描**全部玩家可见字符串**（line 的 label/text、scene 的 display_name、evidence 的 title/summary、interaction 的 label/message）拦截「原初 AI」，并强制 origin_ai 的 label/display 等于 `████`——正式内容替换后校验自动生效，无需改校验代码。

### 4.4 Evidence（C3）

```ts
interface TrialEvidence { evidence_id: string; title: string; summary: string }
```

- `title` = 文字天体上显示的关键词，**硬约束 4–5 个汉字**（orb 排版与可读性要求）；
- `summary` = 点击关键词后展示的证据详情；
- 目前 5 条 Evidence 在两次推理 phase **全部授权**（`authorized_evidence` 全量下发）；标题/详情/是否授权一律由 Backend 下发，前端不按文案猜测。

### 4.5 interaction（C5 字面量，来自 `phases[].interaction`）

`advance / text_input / service_stop_modal / complete` 的 label、`service_stop_modal.message`、`shatter_puzzle` 的 puzzle_id/shard_ids 全部写在 phase 行的 `interaction` 里；`evidence_orbit` 行只写 `kind + deduction_id`，`selection_min/max、allow_retry、seed` 由 Runtime 从对应 deduction 配置补入（单一来源）：

```ts
type TrialInteraction =
  | { kind: 'advance'; label: string }                                  // 如 "开始试玩" / "继续"
  | { kind: 'text_input'; label: string }                               // 如 "发送"
  | { kind: 'shatter_puzzle'; puzzle_id: string; shard_ids: string[] }
  | { kind: 'service_stop_modal'; message: string; label: string }      // message 现为 "AI 停止服务"
  | { kind: 'evidence_orbit'; deduction_id; selection_min; selection_max; allow_retry; seed: number }
  | { kind: 'complete'; label: string }
```

其中 `service_stop_modal.message = "AI 停止服务"`（语义已确认、字面待定，docs/23 §6）与各按钮 `label` 属于待正式化文案；证据轨道 `seed`（内容表 `deductions[].orbit_seed`）由 Backend 下发，前端不再按 deduction_id 猜 seed。

### 4.6 TrialView（下发全量）

前端 `TrialView`：`session_id`（orchestrator 注入）、`experience_id=trial_v1`、`started`、`finished`、`phase_id`、`node`（TrialLine|null）、`scene`、`interaction`、`authorized_evidence[]`、`story_tokens[]`、`outcome`/`reasoning_outcome`（ACCEPTED|NO_MATCH|null）、`route_id`、`fixture_content=true`。

> 与 docs/23 §10.1 的偏差（已实现为准）：暂无独立 `presentation_actions[]`；`fixture_content` 为显式标记（正式内容替换后应翻转/移除）。

## 5. 硬性约束（内容写错 → 拒绝启动 / 400）

### 5.1 载入期校验（fail closed，替换内容时必须全部保留并补全）

| # | 约束 | 现状位置 | 状态 |
|---|---|---|---|
| 1 | Evidence id 无重复 | `content.py::validate_trial_content()`（import 时） | ✅ |
| 2 | Evidence 标题 4–5 汉字 | 同上 | ✅ |
| 3 | 玩家可见文本不得含「原初 AI」；origin_ai 强制 `████` | 同上（扫描全部可见字段 + 单测） | ✅ |
| 4 | 未知角色/场景/证据、引用错位、不可达节点、route 非终态或错配、分支默认不穷尽 → 拒绝启动 | `validate_trial_content()`（13 组校验 + 单测 `tests/test_trial_content.py`） | ✅ 2026-09-05 补齐 |
| 5 | `text_keywords_none`（可选）：给出时必须是非空字符串序列 | `validate_trial_content()`（docs/25 §3） | ✅ 2026-09-05 |

### 5.2 运行期校验（Runtime 已实现）

| 命令 | 校验要点 |
|---|---|
| `ADVANCE` | 仅限白名单转移（§7 表），其余 phase 抛错；进入 `opening_service_stopped` 时幂等授予 `RING` + `RING_ACQUIRED` |
| `PLAYER_INPUT` | 仅 `opening_input` 可发；非空、≤2000 字符；成功 → `OPENING_INPUT_COMPLETED` + 进 `opening_anomaly` |
| `COMPLETE_SHATTER` | 仅 `opening_shatter`；恰好 4 个唯一 shard id；归一化 `x/y` 偏差 ≤0.035、`rotation` ≤4.0；`SHATTER_SOLVED` 幂等 |
| `SUBMIT_REASONING` | 见 §6；message 非空 ≤4000；evidence 非空、去重、必须存在于授权表 |

所有命令带 `command_id`，与 `last_command_id` 相同则幂等返回（防重复提交/重试副作用）。

## 6. Deduction 与 Branch 规格（C4 —— 内容表 `deductions` / `routes`）

两次推理的完整判定现状（自 2026-09-05 起位于 `TRIAL_CONTENT.deductions`；下表即该表的当前值，**正式替换只改这里**）：

### 6.1 第一次推理（phase `fragment_01_first_reasoning`）

| 项 | 现状值 |
|---|---|
| deduction_id | `TRIAL_DEDUCTION_DEEPSEEK_MEMORY` |
| 可选 Evidence 上限 | ≤2（min 1） |
| Evidence Gate | 必须包含 `TRIAL_EV_MEMORY_GAP` |
| 文本等价表达（Fixture） | 归一化（去空格）后含 `失忆 / 记忆断层 / 记不起来 / 忘记 / 想不起来 / 没有那段回忆 / 不记得 / 记不清` 之一 |
| 否定排除（Fixture，2026-09-05 修订） | 归一化文本命中 `text_keywords_none` 任一短语即拒绝，即使含关键词：`没有失忆 / 不是失忆 / 并非失忆 / 没失忆 / 不存在失忆 / 不认为她失忆 / 不觉得她失忆 / 不认为失忆 / 不觉得失忆 / 没有忘记 / 并非忘记 / 没有记不起来 / 不觉得她记不起来 / 没有记忆断层 / 不是记忆断层 / 并非记忆断层`。语义：这些短语断言「缺陷不存在」（否定结论）；「没有记忆」「想不起来」是缺陷本身，属于关键词而非否定 |
| 通过 | `deepseek_truth_revealed=true` + `DEEPSEEK_MEMORY_TRUTH_REVEALED` + 进 `fragment_01_group_intro` |
| 不通过 | `last_outcome=NO_MATCH`，`allow_retry=true`（无限重试、失败不消耗 Evidence，正式提示强度待定） |

### 6.2 第二次推理（phase `fragment_01_group_reasoning`）

| 项 | 现状值 |
|---|---|
| deduction_id | `TRIAL_DEDUCTION_GROUP_TRUTH` |
| 可选 Evidence 上限 | ≤3（min 1） |
| 正确组合（Evidence Gate） | `TRIAL_EV_MEMORY_GAP` 与 `TRIAL_EV_DIALOGUE_FRAGMENT` 都选中 |
| 文本等价表达（Fixture） | 含 `真相 / 身份 / 异常 / 记忆` 之一 |
| **线路映射（穷尽）** | 选中 `TRIAL_EV_IDENTITY_NOISE` → `fragment_02_b`；否则 → `fragment_02_a` |
| 无死路 | 无论 `reasoning_outcome` 是 ACCEPTED 还是 NO_MATCH，都提交 `FRAGMENT_01_ROUTE_COMMITTED` 并进入对应 handoff；`allow_retry=false` |
| 分离原则 | `reasoning_outcome`（文本+证据是否正确）与 `route_id`（仅由证据决定）互不混淆 |

> 注意：文本归一化为 `message.lower().replace(" ", "")`；等价表达只是 Fixture 关键词集合，**正式等价表达需要与正确组合一起由内容侧（用户确认）提供**。`text_keywords_none` 是可选字段（docs/25 §3）：不写 = 无否定排除；群推理当前未配置否定短语，其否定句式误判是已知限制（docs/25 §9）。判定式为 `证据门 AND 任一关键词 AND 非任一否定短语`。

## 8. 与主线剧本格式的差距（正式草稿的扩展位）

主线固定剧本（`story_content.py`，源自 07 剧本 / Prologue markdown）的 step 支持：

| 能力 | 主线固定剧本 | 试玩现状 | 正式草稿是否需要 |
|---|---|---|---|

| `emotion` 字段（走 Backend 允许情绪集） | ✅ | ❌ | 需要（演出随情绪换立绘） |

**接入策略（草稿到位后执行）：** `TrialRuntime` 命令面与 `TrialView` 契约已固定，判定/分支/转移已内容化；草稿只需把「一个 phase = 一条 line」扩展为「一个 phase = 台词序列（line[]，可含 emotion / 演示指令）」——扩展发生在内容表 schema 与前端 node 渲染，不再需要为此改 Runtime 逻辑。
