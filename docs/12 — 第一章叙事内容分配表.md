# 2. 核心原则

第一章正式内容统一采用：

```text
Generative Dialogue
+
Deterministic Narrative
+
Deterministic Critical Disclosure
```

即：

> 语言可以自由，但关键事实首次出现、关键剧情事件和关键Reveal不能依赖模型随机发挥。

第一章不再允许以下三个互相独立的事实来源长期并存：

```text
Script Node
+
Fixed QA
+
AI自由回复
```

正式目标统一为：

```text
Narrative Content
↓
SCRIPT / HYBRID / AI
↓
Character Runtime
```

所有关键台词和关键信息均必须能够追溯到一个正式 Narrative Content Node、Claim、Evidence、Disclosure或Narrative Directive。

# 3. 三种内容模式

正式剧情节点只使用以下三种模式。

---

## 3.1 SCRIPT

完全确定性内容。

适用于：

- 首次登场；
- 重大剧情事件；
- 重要伏笔；
- 关键系统提示；
- 必须保证逐次一致的Reveal；
- 豆包的Scripted Character内容。

流程：

```text
Narrative Event
↓
Script Sequence
↓
固定Presentation / Dialogue
↓
Sequence完成
↓
恢复自由输入
```

SCRIPT阶段不调用生成式Character Runtime决定核心台词。

---

## 3.2 AI

普通自由对话。

适用于：

- 闲聊；
- 角色反应；
- 已公开事实的解释；
- 玩家情绪表达；
- 重复提问；
- 非关键追问；
- 不推进主线的自由互动。

流程：

```text
Player Input
↓
Narrative = NOOP / 非关键Intent
↓
Character Runtime
↓
Validated AI Response
```

AI不得自行Reveal尚未开放的关键Claim / Evidence / Ground Truth。

---

## 3.3 HYBRID

确定性剧情要求 + AI自由语言表达。

适用于：

- 关键角色证词；
- Disclosure；
- GPT Evidence Summary；
- 关键质询后的角色回答；
- 已满足Narrative Gate后的事实承认。

流程：

```text
Player Input
↓
Narrative判断满足条件
↓
生成Narrative Directive
↓
Character Runtime
↓
AI自由组织语言
↓
验证必须表达 / 禁止表达内容
↓
Approved Dialogue
```

HYBRID的核心规则：

> **意义固定，措辞可以变化。**

# 4. 台词冻结等级

内容模式与台词冻结等级分开定义。

---

## 4.1 LOCKED

必须逐字输出。

仅用于极少数关键伏笔或剧情标志句。

例如：

```text
Claude：
“比上一次慢。”
```

此类台词不得交给LLM改写。

---

## 4.2 SEMANTIC_LOCK

必须表达固定语义，但允许角色化措辞变化。

例如：

```text
必须表达：
Claude没有亲眼看到DeepSeek本人。

允许：
“没有。我看到的是记录，不是她本人。”

也允许：
“我没见到她本人。我的判断来自系统记录。”
```

不得改变：

```text
CLAUDE_DID_NOT_VISUALLY_SEE_DEEPSEEK
```

这一事实。

---

## 4.3 DIRECTIVE

仅规定本轮叙事目标与禁止范围。

例如：

```text
目标：
DeepSeek得知当前自己是#04、日志是#03后进行反应。

允许：
惊讶、吐槽、庆幸、与Player讨论。

禁止：
主动解释Recovered Session完整机制。
```

实际措辞由模型自由生成。

---

# 5. 模式与冻结等级组合

推荐：

```text
SCRIPT
→ LOCKED / SEMANTIC_LOCK

HYBRID
→ SEMANTIC_LOCK / DIRECTIVE

AI
→ DIRECTIVE
```

普通AI自由聊天不需要逐句进入本文件。

本文件只规定其：

- 可知信息；
- 禁止提前透露信息；
- 当前Narrative Context。

---

# 6. Script Sequence期间Player Input规则

正式统一：

# SCRIPT_SEQUENCE_ACTIVE → Player Input LOCKED

当正在执行：

- 角色首次登场；
- 系统异常；
- 固定多角色对话；
- 关键Reveal；
- 强制Presentation Sequence；

前端暂时禁止提交新的Player Message。

Sequence结束后：

```text
SCRIPT_SEQUENCE_COMPLETE
↓
Player Input ENABLED
```

目的：

避免：

```text
固定剧情正在播放
+
Player发送自由输入
+
Character Runtime同时产生回复
```

造成Speaker冲突与剧情竞态。

---

# 7. Script Sequence恢复要求

主线Script必须满足：

```text
once
+
idempotent
+
refresh-safe
```

Refresh后不得：

- 重复首次登场；
- 重复写入关键台词；
- 重复Reveal Evidence；
- 重复执行State Change。

具体持久化实现由Runtime决定。

本文档只要求：

> Script Sequence必须可以根据正式Game State判断“是否已经发生”。

# 8. Content Node与story_phase的关系

本文档中的：

```text
CH1-Nxx
```

是：

# Content Authoring Node ID

用于标识剧情内容节点。

它不是新的：

```text
story_phase
```

也不要求增加新的数据库Phase。

当前正式：

```text
Chapter1State.phase

opening
investigation
recovery_required
...
```

以及：

```text
story_phase

prologue
chapter1_investigation
chapter1_recovery_required
...
```

继续有效。

Narrative Runtime可以通过：

- Evidence；
- Claim；
- Contradiction；
- Inference；
- Flag；
- completed_events；
- Character Availability；

判断某Content Node是否可用。

不得为了本文档重新制造一套平行的大型状态机。

# 28. 运行时优先级

同一Player输入可能同时命中多个对话来源时，执行优先级固定：

```text
1. Active SCRIPT Sequence

2. Current Critical Narrative Disclosure
   / HYBRID Claim

3. 豆包 Script Runtime

4. Generative AI Character Runtime

5. Character Safe Fallback
```

不得采用：

```text
Fixed QA先扫一遍
→ Script再扫
→ AI最后扫
```

这种彼此无权威关系的匹配方式。

关键事实必须先由Narrative Gate决定：

> 当前是否允许表达。

之后才决定：

> 用哪种语言形式表达。
