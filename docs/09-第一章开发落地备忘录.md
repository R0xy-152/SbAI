# 第一章开发落地备忘录

## 1. 文档目的

本文档用于提醒开发阶段：

> 当前第一章已经从早期的 ACCS / 门禁漏洞 / Familiarity Residual 等方案，切换为“封闭空间调查 + AI角色证词 + 私审 + Recovery协作 + 权限选择 + Bad End”的新结构。

本文档不规定具体代码写法，不指定具体目录、类名、框架细节，也不替代现有功能文档。

它只回答：

1. 开发前需要清理哪些已废弃内容；
2. 新方案还需要补齐哪些前后端能力；
3. 推荐按什么顺序落地；
4. 每个阶段完成到什么程度才进入下一阶段。

---

# 3. 第一阶段：清理已废弃方案

在继续新增功能前，优先清理已经不再属于当前第一章设计的代码、状态、UI和测试。

目标不是“把所有旧代码都删除”，而是：

> 不允许废弃系统继续影响新剧情状态和新架构。

---

## 3.1 ACCS相关内容

早期 ACCS 设计已经不再作为第一章核心玩法。

需要检查并处理：

```text
ACCS domain logic
门禁权限模拟
authorization cache
permission / role exploit
race condition相关状态
旧Terminal门禁解谜
旧Bug利用流程
ACCS专用UI
ACCS专用测试
```

处理原则：

- 如果只服务于旧ACCS玩法：删除；
- 如果可以复用于普通Terminal展示：保留展示层，移除旧业务逻辑；
- 如果与新Evidence / Investigation系统冲突：优先删除；
- 不为了“以后可能用到”保留复杂死代码。

---

## 3.2 Familiarity Residual相关内容

已废弃：

```text
Familiarity Residual
异常回答速度
回答延迟作为剧情信号
熟练度残留触发
红色按钮熟练度测试
相关Puzzle Phase
相关Prompt Directive
相关UI演出
```

全部不得继续作为第一章剧情依赖。

API响应速度只能视为技术延迟，不能承担玩法语义。

---

## 3.3 旧第一章状态机

检查旧状态中是否存在：

```text
LOG_KEY
ACCS_UNLOCKED
BUG_FOUND
CACHE_EXPLOIT
STALE_PERMISSION
RED_BUTTON_TEST
FAMILIARITY_TRIGGER
```

若已经失去用途：

> 从新第一章主状态机中移除。

旧Save若不要求兼容，可以在当前技术验证阶段直接舍弃，不为废弃版本做迁移负担。

---

## 3.4 旧Prompt与角色知识

重点检查：

- DeepSeek是否仍被告知ACCS知识；
- DeepSeek是否还知道旧Bug；
- 角色Prompt是否包含已经删除的第一章真相；
- Narrative Interpreter是否仍能输出旧Intent；
- Mock Provider是否仍返回旧剧情。

新方案上线前，这些残留必须清理。

在实现复杂AI功能前，先用确定性脚本建立完整第一章主流程。

目标：

> 即使暂时关闭真实LLM，也能从开场跑到Bad End / To Be Continued。

需要具备：

```text

关键事件触发
场景切换
Evidence解锁
私审权状态
Recovery状态
Admin归属
最终Security Review
Bad End
To Be Continued
```

此阶段不追求自然语言体验。

重点验证：

> 整个章节的事件顺序和状态转换是否成立。

---

# 5. 第三阶段：场景调查系统

实现：

```text
调查热点
热点状态
简单互动
纸张涂画
场景事实

```

优先完成最小可玩场景：

```text

```

完成标准：

> Player可以通过实际探索获得第一批Evidence，而不是通过剧情自动塞给Player。

---

# 6. 第四阶段：Evidence与Claim基础层

这是后续调查玩法的核心数据基础。

需要补齐：

```text
Evidence Registry
Claim Store
角色公开证词
Evidence来源
Evidence是否已获得
Evidence是否已出示
角色说过的重要Claim
```

重点：

> Evidence、Claim、Ground Truth必须与LLM对白分离。

LLM说了什么可以变化。

但：

```text
Claude是否看到DeepSeek
03:17发生了什么
谁知道什么
```

必须是稳定数据。

---

# 7. 第五阶段：自然语言询问

在事实层稳定后，再接真实AI。

目标：

```text
Player自由输入
↓
Interpreter识别Intent / Topic / Referent
↓
Backend准备角色允许看到的事实
↓
Character Runtime生成回应
```

核心原则继续保持：

# 语言自由，事实不自由

本阶段重点不是让AI“聪明到什么都能回答”。

而是：

> 无论Player怎么问，AI都不能破坏Ground Truth。

优先支持第一章实际需要的问题类型，不追求通用聊天Agent。

---

# 8. 第六阶段：四角色信息可靠性

自然语言链路稳定后，再分别实现角色差异。

## 8.3 ChatGPT

```text

```

不能简单依赖Prompt要求“表现得腹黑”。

---

## 8.4 豆包

实现：

```text

≠
Interpretation
```

验证：

> 她可以理解错，但不能让底层事实随机变化。

# 10. 第八阶段：单独审问权小游戏

此功能不要过早做。

因为它依赖：

- Evidence
- Claim
- Contradiction
- Character Disclosure

都已经成立。

建议先做一个统一的：

# Evidence Manipulation Framework

然后分别配置：

```text

找信息断层

GPT：
找被遗漏的事实

豆包：
拆Observation与Interpretation
```

DeepSeek默认开放私聊。

完成标准：

> 私审权不是剧情自动给，而是Player通过一次短推理操作获得。

# 12. 第十阶段：Recovery危机小游戏

调查主循环验证好玩以后，再实现第一章的大型合作玩法。

不要提前开发。

需要支持：

```text
Sandbox节点
节点状态
Player行动点
DeepSeek PREVIEW
Claude VERIFY
GPT OPTIMIZE
豆包 PROTECT
```

关键技术要求：

> 不依赖LLM API响应速度。

AI对白可以异步表现。

但：

```text

GPT权限累积

```

# 13. 第十一阶段：Admin归属

Recovery完成后根据Player行为计算：

```text
PLAYER ADMIN
或
GPT ADMIN
```

Admin归属必须来源于此前行为。

不能在结尾突然弹出：

```text
你想让谁当管理员？
```

需要重点测试：

- GPT能力是否真的具有诱惑；
- Player路线是否可行；
- GPT路线是否明显更省力；
- 两条路径都不会卡死。

# 15. 第十三阶段：Bad End

Bad End属于独立Presentation State。

进入后需要主动关闭：

```text
调查
Evidence
角色切换
私审
Recovery
普通剧情推进
```

只保留：

```text
Player
ChatGPT
自然语言输入
```

并进入独立：

```text
BAD_END_CHAT_STATE
```

重点：

> Bad End不是普通结局CG，而是一个新的长期对话状态。

---

# 23. 开发阶段最重要的约束

如果后续实现过程中出现设计冲突，优先级按以下顺序判断：

```text
1. 玩家是否真的在做决定和推理
2. Ground Truth是否稳定
3. AI角色是否符合各自信息规则
4. AI失败是否会阻断主线
5. 状态是否可恢复和测试
6. 最后才考虑演出复杂度
```

---

# 24. 需要避免重新走回去的方向

不要重新加入：

```text
为了展示AI而设计的AI小游戏
依赖API响应速度的机制
复杂Terminal字段编辑
玩家只是把信息复制给AI
AI直接给谜题答案
LLM决定剧情真相
所有角色靠撒谎制造悬疑
过早实现Deadlock / Sandbox完整技术模拟
```

第一章当前最重要的是验证：

> **AI角色是否真的可以成为“可调查、可质疑、可建立信任”的角色。**

而不是验证系统能否模拟真实计算机安全机制。

# 25. Definition of Done

第一章开发完成至少满足：

```text
Player可以从开场独立玩到结尾

四个AI依次出现

调查 / Evidence / 自由询问 / 出示Evidence
/ 指出矛盾 / 阶段推论 / 私审均可使用

AI语言自由但不会破坏Ground Truth

Recovery小游戏可玩

Player或GPT可以获得Admin

四AI完成最终自证

Bad End可以稳定进入

Bad End后只剩GPT并保持自然语言对话

其他路线稳定进入To Be Continued

Refresh后关键状态可以恢复

Mock Provider完整跑通

真实Provider失败不会破坏主线
```

达到上述状态以后，再进入第二章设计。
