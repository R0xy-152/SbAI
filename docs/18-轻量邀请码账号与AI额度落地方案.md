# 18 — 轻量邀请码账号与 AI 永久额度落地方案

> **文档状态：** Active
> **日期：** 2026-08-21
> **适用阶段：** 线上小规模展示

## 0. 决策摘要

- 复用 FastAPI、PostgreSQL 与 Nginx，不增加 Redis、认证服务或新容器。
- 一人一个可重复邀请码；无注册、邮箱、密码、找回与管理网页。
- 整个应用需要登录；仅登录接口、健康检查与登录页静态资源公开。
- 每账号默认永久 100 次 AI 对话，可由服务器 CLI 追加。
- 现有匿名存档与会话在部署切换时删除，不迁移。
- 当前 HTTP 入口仅用于受控展示，Cookie 暂不设置 `Secure`；正式开放前必须切换 HTTPS 并启用。

## 1. 身份与会话

邀请码由至少 128 bit CSPRNG 随机值生成，可跨设备重复登录。数据库只保存邀请码的 HMAC-SHA256；明文只在 CLI 创建或轮换时显示一次。

登录成功后签发不透明随机会话令牌。浏览器仅通过 `HttpOnly`、`SameSite=Lax` Cookie 携带令牌，数据库只保存令牌 SHA-256；会话绝对有效期 30 天。账号停用或会话撤销后立即失效。

Frontend 不再生成或提交 `player_id`。Backend 从登录会话取得 `user_id`，并对 Save、Active Session、History 及所有游戏操作执行归属校验。非本人资源统一表现为不存在。

## 2. 数据与额度

PostgreSQL 新增：

- `users`：身份、显示名、邀请码摘要、状态、额度总数/已用数；
- `auth_sessions`：会话令牌摘要、用户、过期/撤销时间；
- `game_session_owners`：运行时 `session_id` 与用户的唯一归属。

`game_saves.player_id` 保留现有列名以减少迁移面，但其值改为后端认证得到的内部 `user_id`，不再接受客户端命名空间。

`POST /api/chat` 在调用游戏运行时前用条件式 PostgreSQL `UPDATE ... WHERE quota_used < quota_total RETURNING` 原子预扣 1 次：成功响应保留扣减；参数、权限、Provider 或服务失败则退回；无额度返回 429 且不调用 Provider。固定故事、读写存档和其他游戏操作不扣额度。

## 3. API 与运维

- `POST /api/auth/login`：邀请码换 Cookie；
- `GET /api/auth/me`：账号显示名与额度；
- `POST /api/auth/logout`：撤销当前会话并清 Cookie；
- Chat response 增加 `quota_remaining`；
- CLI 支持创建、列出、追加额度、停用、轮换邀请码、撤销登录会话；
- Nginx 仅对登录端点做内存级限速。

部署时先备份 PostgreSQL，再清空旧 `game_saves` 与 `backend/data/sessions/*.json`，配置 `GAL_AUTH_SECRET`、`GAL_AUTH_COOKIE_SECURE=false`，创建首批展示账号后切流。切换 HTTPS 时只把 `GAL_AUTH_COOKIE_SECURE` 改为 `true`。

## 4. 明确限制

- 邀请码被分享后，多设备共享存档和额度；
- HTTP 下邀请码和 Cookie 可能被链路窃取；
- 预扣后进程崩溃可能损失 1 次额度，由 CLI 人工补回；
- 当前阶段不引入额度流水、支付、自动重置或用户自助管理。
