## 0. 结论

当前 `Vue 3 + TypeScript + FastAPI + PostgreSQL/JSON Session + Docker Compose` 技术栈可以满足本需求，**无需更换框架，也无需为核心玩法引入 Redis、RAG、微服务或通用 WebGL 引擎**。2026-09-04 的首轮实现和桌面浏览器全流程验收已经验证这一路线可工作；§18 已批准的 Live2D P1 例外由 Cubism SDK 在单一 Canvas 内使用 WebGL，不改变整体架构。

但这不是现有配置换皮即可完成的功能。当前真正缺少的是：

1. 一个与既有序章/第一章隔离、能够串起混合交互节点的确定性 `TrialRuntime`；
2. 一个“四片玻璃破裂并拼回”的可交互前端模块；
3. 一个“文字天体 + 查看证据 + 拖入推理槽 + 自由文本提交”的前端模块；
4. 试玩版自己的 Evidence / Deduction / Branch 配置与存档状态。

整体判断：**技术可行，后端风险中等，前端演出与交互风险中高；最大风险不是 LLM，而是玻璃拼图的视觉可信度、文字多体运动的可读性，以及尚未定稿的内容判定表。**

## 4. 开局：固定剧情与输入引导

### 4.1 目标

- 建立 Player 与原初 AI 已相识很久、感情深厚的既有关系；
- 让深夜闲聊具有真实情侣对话感；
- 通过一次或多次自然语言输入，让玩家在第一个异常发生前完成核心输入教学；
- 异常发生和后续破裂必须由确定性 Runtime 触发，不能由 LLM 自行决定。

### 4.2 首轮实现采用的回复方式

“固定对话开局”与“玩家可输入任意文字后仍像真实闲聊”之间存在实现选择：

| 方案 | 优点 | 风险 |
|---|---|---|
| 全固定回复 | 稳定、零模型延迟、剧情节奏完全可控 | 玩家输入与下一句可能语义不衔接 |
| 固定关键节拍 + 1~2 轮受控生成回复 | 最接近真实聊天；异常仍可按固定回合触发 | 需要新增原初 AI 角色配置、上下文权限和输出校验 |
| 固定关键节拍 + 确定性意图分桶回复 | 无 Provider 风险，比完全固定更衔接 | 需要额外编写多组回复，仍可能显得模板化 |

首轮可玩实现暂用“全固定关键节拍”：玩家输入会写入 History，随后由 `TrialRuntime` 确定性进入异常节点；不调用 LLM 生成原初 AI 回复。此选择只用于验证核心闭环，正式内容仍需用户确认。无论后续选择哪种方式，所有关键台词、异常发生点、演出开始点都必须来自内容配置或 Narrative Event；玩家输入和 LLM 原始输出不能直接改状态。

## 5. 演出 1：四片玻璃破裂与拼合

### 5.1 视觉语义

- 破裂对象是玩家刚才看到的**整块游戏画面**，视觉上像一整块现实玻璃；
- 画面分成四个不规则玻璃状碎片；
- 四片的源面积应尽量一致，建议每片占完整画面的 `22%~28%`；
- 四个多边形必须完整覆盖原画面，源状态不得重叠或留下非设计缝隙；
- 破裂后原画面冻结，防止碎片内部内容继续打字、换立绘或与底层 UI 不同步。

### 5.2 推荐实现

不截取任意 DOM，也不引入 `html2canvas`。在固定剧情节点生成一个与当前画面一致的只读 `TrialStageSnapshot`，四个碎片各渲染同一快照，再用预定义 SVG/CSS polygon mask 裁出对应区域：

```text
TrialStageSnapshot（冻结）
  ├─ shard-1 + polygon-mask-1
  ├─ shard-2 + polygon-mask-2
  ├─ shard-3 + polygon-mask-3
  └─ shard-4 + polygon-mask-4
```

这样可以保持背景、角色、对话框和文字都像同一块画面，同时避免跨域图片、字体、动态 DOM 截图和四份活组件状态同步问题。

### 5.3 交互规则

- 鼠标与触控统一使用 Pointer Events；每片支持 pointer capture；
- 首版支持拖动；高性能档启用基于面积质量、转动惯量、角速度、阻尼和弹簧吸附的刚体近似。初始旋转在接近正确位置时受弹簧扭矩平滑归零，玩家不需要额外学习旋转手势；
- 进入吸附半径后采用缓动靠拢，不瞬移；
- 单片归位后仍可在尚未提交完成前撤回，四片全部归位才出现完成状态；
- 刷新或读档回到拼图开始状态，不要求保存每一像素的中间拖动位置；
- `prefers-reduced-motion` 下保留拼图本身，但缩短飞散动画并取消强烈闪烁。

物理质量按运行时帧预算自适应：高档使用更小固定步长和更多子步，中档减少子步，低档保留同一力学规则但降低更新频率与装饰效果。能力判断以实际帧耗时为主，`hardwareConcurrency` 等提示只作辅助，不能仅凭设备型号硬编码。

### 5.4 权威提交

Frontend 只维护拖动中的表现状态。四片看似归位后提交每片的归一化位置/角度；Backend 校验：

- 当前 Phase 必须是 `opening_shatter`；
- 恰好包含四个唯一 shard ID；
- 每片位置与角度均在配置容差内；
- `SHATTER_SOLVED` 尚未提交。

校验通过后，Narrative Runtime 幂等提交 `SHATTER_SOLVED`，才允许进入残存意识台词与戒指获取。Frontend 不得仅凭本地动画直接推进剧情。

## 6. 演出 2：AI 停止服务

- 戒指获取必须先由 Backend 提交，再进入演出 2；
- 屏幕中央展示高优先级红色系统弹窗，文案按用户给出的语义为“AI 停止服务”，最终字面文本待内容确认；
- 弹窗是注册过的 Named Presentation，而不是 Runtime 下发任意 HTML/CSS；
- 弹窗出现时锁定底层输入与系统推进；
- 首轮实现采用玩家点击“继续”后进入片段 1；该行为由 Backend 的 `ADVANCE` 转移确认，不由 Frontend 自行跳转；
- 该节点完成后自动存档，避免刷新导致重复授予戒指。

## 7. 玩法 1：文字天体推理场

### 7.1 玩家操作闭环

```text
观察持续运动的关键词
  ↓
点击某个关键词 → 查看证据详情
  ↓
把认为关键的证据拖入“推理槽”
  ↓
在输入框写下自己的推理
  ↓
提交 evidence_ids[] + message
  ↓
Backend 校验证据权限、前置条件、正确性与分支
  ↓
返回角色反应 / 下一 Phase / 线路结果
```

关键词只是 Evidence 的可视入口。标题、详情、是否已获得、当前是否可选均由 Backend 下发；Frontend 不得根据文案猜测正确证据。

### 7.2 文字物体约束

- 一个关键词是一个不可拆分的完整物体；首版内容标题必须控制在四至五个汉字；
- 所有物体的惯性质量与引力质量相等；字体宽度只影响安全间距，不影响质量；
- 文字保持水平可读，不随速度旋转；
- 点击与拖动用位移阈值区分，避免想查看详情时误拖；
- 拖动中的文字物体必须暂时脱离物理场裁切，并显示在右侧推理槽之上；松手后若未命中推理槽，则恢复到场内，不能卡在左右 UI 的分界线上；
- 拖入推理槽后，该证据退出物理场并以稳定卡片显示；撤回后重新以受控速度加入；
- 当前可提交证据数量由 Backend 对应 deduction 配置下发，接口统一使用去重的 `evidence_ids[]`，不把数量写死在 Frontend。

### 7.3 多体运动实现

首版不引入通用物理引擎。把物理求解器实现为纯 TypeScript 模块，由 `requestAnimationFrame` 驱动固定时间步长模拟：

```text
两两软化引力
+ 安全距离内的连续柔性排斥
+ 中距离成对切向轨道力
+ 极弱中心回归力
+ 边缘柔性约束
+ 速度/加速度上限
+ 轻微阻尼
= 下一帧位置
```

两两吸引使用软化距离，避免距离趋近于零时加速度爆炸：

```text
a(i←j) = G × (position[j] - position[i])
         / (distance² + epsilon²)^(3/2)
```

碰撞代理按胶囊文字的真实外接范围设置，不能只按字框短边估算。当两个文字包围体进入安全距离时，用连续 `smoothstep` 权重逐渐增加排斥力；接触前再根据相对速度预测最近接距离并施加对称侧向避让，不等实际碰撞后再纠正。中距离内加入等大反向的成对切向轨道力，优先延续两体已有角动量，使双体互绕、三体扰动和轨迹交织成为常态；靠近安全边界时切向力平滑退出，让排斥优先。不得使用刚性反弹、瞬时改方向或事后瞬移分离。固定步长、最大子步数、速度上限和边缘软约束共同防止穿透与整群飞出屏幕。

该方案适合小规模关键词集合。正式 Evidence 数量确定后必须在目标最低性能设备上基准测试；若同屏数量显著超过约 20 个，需要重新评估可读性和性能，而不是直接提高引力计算复杂度。

### 7.4 可测试性与稳定性

- 初始位置和初速度来自可注入 seed，生产每局可变化，测试可复现；
- 物理求解器是无 DOM 的纯模块，单测覆盖等质量、成对力动量守恒、软排斥、预测避让、速度上限、中心回归和多 seed 长时间无重叠；
- 浏览器标签进入后台时暂停模拟，回来后不补算巨量时间差；
- Resize 后按归一化坐标重投影，并执行平滑安全分离；
- Playwright 使用固定 seed 和固定 clock 做交互/视觉验证；
- 减少动态效果模式可降速或暂停自由漂移，但仍允许点击和拖入推理槽完成玩法。

## 8. 片段 1 的两次推理

### 8.1 DeepSeek 单人审问收尾

- 开场直接处于审问收尾，不在本文补写此前发生的审问内容；
- 在场角色由 Backend 限定为 DeepSeek；
- 玩家通过玩法 1 选择关键 Evidence 并输入推理；
- Backend 先校验 Evidence 已授权，再匹配预定义 Deduction；
- 只有 Narrative Runtime 可以提交“DeepSeek 的失忆真相已被揭露”；
- 提交后通过权威 Presentation State 让全人物集合登场。

按用户当前描述，第一次推理必须成立后才进入集合。首轮实现允许无限重试，失败不消耗 Evidence，并明确提示玩家调整证据或推理文本；正式提示强度与次数限制仍可后续调整。

### 8.2 全人物集合推理

第二次提交必须拆开两个互不混淆的结果：

1. `reasoning_outcome`：玩家的证据与文字推理是否成立；
2. `route_id`：由所选 Evidence 按预定义、穷尽的规则映射到线路 A 或 B。

无论 `reasoning_outcome` 是正确、错误还是部分成立，都必须进入片段 2；不得因判定失败形成死路。线路只由 Evidence 选择决定，输入文字不能偷偷改变线路。

具体 Evidence ID、正确组合、等价表达、线路 A/B 映射与角色反应均为内容真相，当前是 `TBD`。实现前必须形成独立内容配置，并保证所有合法提交都能确定映射到且只映射到一个线路。

## 10. 模块与接口设计

### 10.1 后端深模块

新增 `TrialRuntime`，把节点编排、Gate、戒指提交、两次推理、线路选择、快照恢复隐藏在一个深模块内部。调用方只需要理解小接口：

```text
current(session_id) -> TrialView
handle(session_id, TrialCommand) -> TrialView
snapshot(session_id) -> TrialStateSnapshot
restore(session_id, TrialStateSnapshot) -> None
```

HTTP 层保持薄：

```text
GET  /api/trial/current
POST /api/trial/command
```

`TrialCommand` 使用受限联合类型，而不是任意 action 字符串：

```text
ADVANCE
PLAYER_INPUT { message }
COMPLETE_SHATTER { shards[] }
SUBMIT_REASONING { deduction_id, evidence_ids[], message }
```

`TrialView` 只下发当前玩家有权看到的信息，至少包含：

```text
session_id
experience_id
phase_id
node
scene
interaction
authorized_evidence[]
presentation_actions[]
story_tokens[]
```

正确 Evidence 组合、失忆真相 Gate 和分支映射不能出现在响应中。

### 10.2 内容与 Runtime 分离

建议目录职责：

```text
backend/app/trial/content.py      # 台词节点、Evidence、Deduction、Branch 配置
backend/app/trial/runtime.py      # 状态机、校验、提交、快照
backend/app/api/trial.py          # HTTP adapter
```

具体台词不应写进 `runtime.py` 或 Vue 文件。内容载入时 fail closed 校验：重复 ID、未知角色、未知 Evidence、不可达节点、非穷尽分支、超出四至五字的关键词标题都应拒绝启动。

### 10.3 前端模块

```text
frontend-vue/src/views/TrialView.vue
frontend-vue/src/components/trial/TrialStage.vue
frontend-vue/src/components/trial/ShatterPuzzle.vue
frontend-vue/src/components/trial/EvidenceOrbit.vue
frontend-vue/src/components/trial/ReasoningTray.vue
frontend-vue/src/components/trial/ServiceStoppedModal.vue
frontend-vue/src/components/trial/physics.ts
```

`TrialView` 负责取当前 View、提交 Command 和切换当前交互模块；物理算法、拼图拖动和证据槽不要继续堆进现有已很大的 `StoryView.vue` 或 `GameView.vue`。

### 10.4 可复用模块

- `GameBackground`、`GameRolesStage`、`GameDialog`、History/System Menu；
- 后端 Session Repository、账号权限、Save Repository、自动存档；
- Presentation State 的多角色站位、情绪与命名演出思想；
- Evidence 的不可变定义、已获得状态与授权详情；
- Deduction 的 Evidence Gate、幂等提交和 `NO_MATCH/BLOCKED/ACCEPTED` 结果语义；
- Ops 事件记录与现有 Docker Compose 部署。

复用的是模块能力和接口原则，不是旧第一章的 Evidence/Claim/Inference ID。

## 11. 存档、恢复与兼容

当前 `story_cursor`、`_story_runtime_for` 和前端 `saveTargetRoute` 只区分 legacy story、prologue 与 game，不能直接识别第四种体验。

推荐最小兼容方案：

- `PersistedSession` 新增可空 `trial_state`，旧快照缺失时为 `None`；
- Save Snapshot 增加 `experience_id = trial_v1`，`chapter_id = trial_v1`；
- Load 结果下发 `experience_id`，前端映射到 `/trial`；
- 不改变旧 `story_cursor` 的结构和解释；
- 一个新试玩会话只属于一种 Experience，禁止同一 Session 同时激活 prologue/legacy/trial；
- 每个关键 Event 后持久化，场景边界自动存档。

至少设置以下自动存档点：

1. 输入引导完成；
2. `SHATTER_SOLVED` 提交；
3. 戒指获取并进入停止服务弹窗；
4. 第一次推理成立；
5. 最终推理与线路提交。

拼图中间坐标和文字天体瞬时轨道不属于剧情真相，不写数据库；刷新时从对应交互节点的稳定初始状态恢复。

## 14. 验收标准

### 14.1 冻结与兼容

1. 序章、既有第一章、终章相关内容及旧调查入口没有字面或状态回归；
2. 旧存档按原路径恢复，新试玩存档只进入 `/trial`；
3. 试玩 Evidence/Flags 不进入 `NarrativeState.chapter1`；
4. 不新增背包、装备或通用道具系统。

### 14.2 开局闭环

1. 玩家至少完成一次明确的自然语言输入教学；
2. 异常和 UI 破裂只能在权威节点触发；
3. 画面恰好分为四个不规则、面积近似的碎片；
4. 鼠标与触控均能拼合，四片未完成时不得进入后续；
5. 完成后只授予一次戒指；
6. 停止服务弹窗出现后才可进入片段 1；
7. 刷新/重复提交不会重复授予或跳过节点。

### 14.3 玩法 1

1. 每个关键词保持四至五字完整显示，运动中不自转；
2. 长时间运行无接触、重叠、穿透、刚性反弹和明显中心绕转；
3. 可稳定形成双体绕行、三体扰动与近距离掠过；
4. 点击能查看当前授权的 Evidence 详情，拖动能选入推理槽；
5. 未获得/未授权 Evidence 即使伪造 ID 也被 Backend 拒绝；
6. 第一次推理不能靠提前说出真相绕过 Evidence Gate；
7. 第二次推理无论正误都提交，且 Evidence 选择唯一决定 A/B；
8. 正确性、线路与 Event Commit 均能存档恢复。

### 14.4 性能与可访问性

1. 目标最低设备上动画稳定、拖动跟手；
2. 标签页后台/恢复不发生位置爆炸；
3. Resize 后不丢失可交互对象；
4. 减少动态效果模式仍可完成全部玩法；
5. 视觉回归使用固定 seed，不因随机轨道产生不稳定截图。

## 18. Live2D 暖色背光开局：排期决策

### 18.1 决策

**已批准排进日程，但不进入当前核心闭环的 P0，也不在素材未齐时立即引入 SDK。** 将其列为 `P1 / Visual Vertical Slice`：在原初 AI 正式人设图、开局对白和目标设备基线确认后，先做一次有退出条件的技术/美术 Spike；通过门槛后再进入试玩版公开测试版本。

原因：Live2D 对本作最有价值的地方不是“角色一直会动”，而是让开局唯一的情感锚点拥有极轻微、近乎记忆投影的生命感。它能明显放大破裂前后的反差，但不会修复剧情内容、推理规则或闭环问题，所以不能抢在这些内容定稿之前成为主进度阻塞项。

> 2026-09-05 更新：**暖色背光的开局特写已由一段视频替代**——用户提供 `kei.mp4`（单镜头暖色逆光特写，117s，4K），已转码 `backgroud/kei_opening_720p.mp4`（7.8MB，默认）/`kei_opening.mp4`（1080p，27MB）+ `kei_opening_poster.png`（首帧回退），接入口径见 docs/27 §7.1。它已满足「极轻微、近乎记忆投影的生命感」，因此本节的 Live2D Spike 由入场候选降为**可选增强**；仅在日后想升级为程序化动态建模时再评估。异常节拍（暖光收窄→冻结）仍按 §18.2 在该视频上叠加，冻结帧作为四片玻璃裁切源（替代 §18.3 的 Live2D 稳定帧捕获）。

### 18.2 氛围定义

“忘妻回忆录”的感觉暂按以下视觉语言理解：

- 暖金色主光从角色背后进入，面部保留柔和阴影，像一段被美化、又看不完全真切的亲密记忆；
- 动作克制：呼吸、眨眼、细微侧头、发梢与衣摆的低振幅惯性，不做直播式持续大幅摆动；
- 对话停顿时动作比说话时更重要；不做实时面捕、摄像头输入和全程口型追踪；
- 名字仍只显示 `████`，模型视觉也不提供可反推出“原初 AI”称呼的文字信息；
- 异常前暖色与柔焦逐步收窄，异常后背光断续、参数轻微失配，再冻结为演出 1 的破裂源画面。

如果用户所指的“忘妻回忆录”不是上述“暖色背光、亲密但不可靠的记忆感”，需在美术 Spike 前补一份参考图或情绪板，避免只按词面误读。

### 18.3 与现有玻璃演出的接法

不让四块碎片各自运行一份 Live2D。异常发生时只做一次稳定帧捕获：

```text
单一 Live2D Canvas 正常渲染
  ↓ 异常 Event
冻结 motion / physics
  ↓ 捕获同一帧到离屏纹理或位图
现有四片 ShatterPuzzle 裁切该冻结帧
  ↓
停止并释放 Live2D 渲染循环
```

这样四片永远来自同一时刻，既不会出现眼睛/发丝在不同碎片里不同步，也避免四倍 WebGL 绘制成本。低性能档、加载失败与 `prefers-reduced-motion` 继续使用当前静态剪影/立绘回退，剧情 Gate 不依赖 Live2D 是否成功加载。

### 18.4 建议日程与 Gate

| 里程碑 | 预计投入 | 产物 | 进入条件 |
|---|---:|---|---|
| V0 静态色彩稿 | 美术/前端 0.5~1 天 | 暖色背光、轮廓遮蔽、异常前后两帧 | 开局构图方向确认 |
| V1 单模型 Spike | 前端 2~3 天；模型制作另估 | Vue 页面单 Canvas、idle/blink/侧头、暂停/恢复、静态 fallback | 获得可用 `.model3.json` 模型及动作 |
| V2 玻璃演出接线 | 前端 1~2 天 | Live2D 稳定帧捕获 → 四片拼图 | V1 达到帧预算且冻结帧无黑屏 |
| V3 内容与性能验收 | 1~2 天 + 目标设备 | 暖色调参数、异常节拍、桌面/移动降级报告 | 正式对白、动作节拍、设备清单确定 |

Go/No-Go 门槛：

1. 目标高性能档前台运行达到 60 FPS 预算，降级档可稳定 30 FPS，拖动玻璃时不同时运行 Live2D；
2. 页面隐藏/恢复、路由离开和 WebGL context lost 均能恢复或切到静态图，不丢剧情状态；
3. 模型加载失败不阻断输入、异常、拼图和存档；
4. 盲测时暖色背光确实提高“亲密回忆 → 服务停止”的情绪落差，而不只是增加技术感；
5. 发布前完成 Cubism SDK 的许可分类确认。官方当前允许先免费验证开发，但发布许可会按主体与应用类别判断；AI/Chatbot 与可扩展应用另有专门规则。

### 18.5 已批准边界

2026-09-04 用户已批准该 Scope Change，仓库硬规则同步改为：允许在 `/trial` 开局表现层验证并接入单角色、单 Canvas 的 Live2D。批准不等于立即下载 SDK；V0 素材和许可分类没有达到准入条件前，不加入运行时依赖。

Live2D 不能成为剧情状态源，动作结束回调不能直接推进剧情，模型视觉信息不能进入 DeepSeek 或其他角色 Context。既有序章、第一章、终章继续冻结。不得顺势扩成换装、模型上传、面捕、直播口型或多角色同屏系统。

### 18.7 Live2D 素材与前置条件清单

#### A. 最低可开工素材包（由内容/美术侧提供）

1. **角色正面半身分层 PSD**：RGB、8 bit/channel、sRGB；目标构图至少覆盖头顶到腰部，按最终最大显示尺寸预留清晰度，不接受只有合成 PNG 的正式建模输入；
2. **可动部件分层**：脸部底色、眉、眼白/虹膜/瞳孔/高光、上下睫毛/眼睑、嘴部、前/侧/后发束、耳朵、颈部、躯干、服装、饰品、阴影、高光与背光边缘光。被头发或脸遮住但运动时会露出的区域必须补画完整；
3. **美术定向包**：角色设定或正面参考、服装/发饰细节、3~5 张只用于方向沟通的情绪板、暖色背光色稿，以及异常前/异常时两张关键帧；
4. **动作节拍表**：至少定义 `idle`、自然眨眼、呼吸/发梢物理、轻微侧头、温柔表情、察觉异常、冻结前失配七个状态；逐句标注何时切换，不由模型自行解释对白；
5. **静态回退图**：与正常和异常构图一一对应的透明 PNG/WebP，Live2D 加载失败、低性能档和减少动态效果时直接使用；
6. **权利材料**：原画/建模/动作的作者与商用授权归属、是否使用第三方素材、模型署名要求；没有明确发布权时只允许本地 Spike。

首轮最小包可以只做**正面半身**，不需要三视图和全身拆件；但若发型、服装结构仅凭正面无法判断，则必须补局部设定图。官方导入要求以 PSD 为主，图层组会转换为纹理/ArtMesh；PSD 需使用 RGB、8 bit/channel，官方建议 sRGB。

#### B. 建模/绑定交付物

- 可继续编辑的 Cubism 工程源文件（`.cmo3`）及使用的 Cubism Editor 版本；
- Web 运行包：`.moc3`、`.model3.json`、纹理图集 `.png`；按实际效果附 `.physics3.json`、`.motion3.json`、`.exp3.json`、`.pose3.json` 和 `.userdata3.json`；
- 参数表：参数名、范围、默认值、动作/表情所用参数与互斥关系；
- 动作至少有短循环 idle 和独立异常动作，首轮不做实时面捕、麦克风口型或逐音素 Lip-sync；
- 控制 Draw Order、Clipping Mask、混合模式和纹理图集切换次数；纹理图集尺寸按目标设备分档，不默认把编辑器最高分辨率原样发到 Web。

#### C. 工程准入条件

1. 锁定 Cubism SDK for Web 版本并记录 Core/Framework 版本、获取来源与许可结论；
2. 只建立一个生命周期适配器：`load → mount → play/pause → freezeFrame → dispose`，Vue 组件不直接承担剧情推进；
3. 确认模型和纹理的同源/CORS、缓存版本号、首包体积预算、加载进度与失败超时；否则 Canvas 冻结帧可能因跨域资源污染而无法导出；
4. 先验证冻结帧能稳定交给现有四片玻璃裁切，再接正式模型；路由离开、后台标签和 WebGL context lost 必须释放或回退；
5. 先确定至少一台桌面最低设备和一台手机最低设备，记录分辨率、DPR、浏览器与内存；验收仍采用 §18.4 的 60/30 FPS 门槛；
6. 剧情侧提供最终固定对白与“对白句 → 表情/动作 → 异常 Event”节拍表；所有剧情 Gate 继续由 Backend Event 确认；
7. 发布前完成 Live2D SDK 的应用类别与 AI/Chatbot 许可复核；若未来允许用户上传/切换不定量模型，必须重新做 Expandable Application 审查。

#### D. 当前缺口与开工顺序

当前仓库还没有可发布的原初 AI 分层 PSD、Cubism 模型包、动作节拍表、目标设备清单或已记录的发布许可结论。因此现在先进入 **V0 美术定向/素材拆分**，同时用一份具备合法测试权的临时模型完成 V1 生命周期 Spike；正式模型未齐不阻塞文字天体和核心闭环。V0 通过后才锁 SDK 版本并加入依赖。
